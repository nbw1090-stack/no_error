# Result v0.0.1 — 接入 openUBMC LLM Wiki（Karpathy 模式）

> 本文件是 **0.0.1** 版本的效果存档：记录「LLM Wiki 接入」的实现方法 + 验证结果。
> 版本号与 [CHANGELOG.md](../CHANGELOG.md) / [VERSION](../VERSION) 绑定。

日期：2026-06-29 ｜ 文档来源：`https://gitcode.com/openUBMC/docs.git`（VitePress 站点）

---

## 一、目标

让 ReAct agent 在日志分析或回答问题时，能参考 **openUBMC 架构知识库**，理解 BMC 的设计
（微组件模型、mdb/D-Bus/Redfish 接口、各特性设计等），并把文档知识与**源码、日志**结合作答。

采用 Andrej Karpathy 的 **「LLM Wiki」模式**（2026.4）：不是把原文切片做关键词/向量检索，
而是让 **LLM 把原始文档提炼成一套结构化、互相链接的 markdown 知识库**，agent 像翻 wiki 一样
「读索引页 → 读整页」导航。

## 二、实现方法

### 1. 全局共享知识库（有意区别于按用户隔离的数据）
openUBMC 文档对所有用户一致、公开只读，因此 wiki 是**单一全局库**（`backend/data/wiki/`），
编译一次、所有用户的 agent 共用。这是对「按用户隔离」不变量的有意例外。

### 2. 存储：磁盘 markdown（`backend/wiki/store.py`）
- `index.md` —— LLM 写的「架构总览」+ 按 section 分组的目录（每页 slug/标题/简介）。
- `pages/<slug>.md` —— 每篇提炼页（页内 `[[链接]]`/相对链接互链）。
- `manifest.json` —— 来源 git/commit、编译模型/时间、各页元信息（含 `source_hash` 供增量）。

### 3. 编译：LLM 逐篇提炼（`backend/wiki/compile.py`）
- `plan_sources`：只选**精选架构核心**——`design_reference`(128) + `api`(52) +
  `quick_start`(10) + `glossary`，实测 **191 篇**源文档（`specifications` 的 1531 篇自动生成
  字典被排除）。贴合 LLM Wiki「有限主题集」定位，成本可控。
- `compile_page`：每篇源文档调一次 LLM，按固定结构（# 标题 / > 简介 / 概述 / 关键设计·接口 /
  相关主题）提炼成一页 markdown。
- `interlink`：编译后轻量后处理，把页正文里出现的其它页标题改成页内链接。
- `build_index_overview` + `render_index`：LLM 基于架构总文档 + 各页标题/简介写总览，
  再拼出分组目录页。

### 4. 同步编排（`backend/wiki/service.py`，SSE）
克隆（blobless+sparse 只拉 `docs/zh`）→ 规划 → **有界并发**（信号量=4）逐页提炼，按完成顺序
推进度 → 互链落盘 → 写索引/manifest。**增量可续编**：`source_hash` 未变的页直接复用，
不重复调 LLM；源文档删除的旧页自动清理。无 LLM（未配 `LLM_API_KEY`）时报错提示。

### 5. agent 接入（与 log/source 工具组同构）
- **wiki 工具组**：`get_wiki_index`（读索引/目录）、`read_wiki_page(slug)`（读整页）、
  `search_wiki(query)`（关键词检索兜底）。
- `core.py` 每轮查 `wiki.store.is_indexed()`，已编译则把 `wiki` 加入 `exposed_groups` 并注入
  `WIKI_GUIDANCE_PROMPT`（引导「先读索引页、再读整页，找不到再检索」）。三种模式
  （有日志 / 无日志有源码 / 纯问答）均生效；Langfuse 托管 prompt 路径也会补上 wiki 指导段。
- 前端「Wiki 知识库」面板：编译按钮 + 逐页进度（compiled/reused/failed）+ 已编译页清单。

## 三、验证结果（全离线）

| 项目 | 结果 |
|---|---|
| 精选源规划 | 真实文档 → **191 篇**（api 52 / design_reference 128 / quick_start 10 / glossary 1），slug 全唯一，`specifications` 自动字典已排除 |
| 编译流水线 | 假 LLM 跑通 plan→compile→interlink→index→manifest；落盘 + 读回 + 检索一致 |
| 增量续编 | 二次同源同步：全部 `reused`、`compiled=0`，LLM 调用大幅减少（仅索引总览 1 次） |
| agent 工具 | wiki 编译后 `exposed_groups` 含 `wiki`、prompt 注入页导航指导；未编译则均无 |
| 后端测试 | 新增 **21 条** wiki 用例（store/compile/工具/端点，全离线）+ 更新分组用例，**全套 322 通过** |
| 前端 | `tsc -b && vite build` 通过 |

> 注：真实编译需调用 LLM（DeepSeek），191 篇约「百万 token 量级」一次性成本，属管理员一次性
> 操作且可增量续编；本版验证用假 LLM 离线跑通全流程，未产生真实 LLM 费用。

## 四、使用方式

1. 登录 → 前端「Wiki 知识库」Tab → 点「用 LLM 编译知识库」（或 `POST /api/wiki/sync`）。
2. 编译完成后，agent 在架构/设计/接口类问题上会自动 `get_wiki_index → read_wiki_page`，
   并把文档结论与日志、源码证据结合作答。

## 五、后续可改进

- 互链可由 LLM 在编译时直接产出（更准），替代当前的标题匹配后处理。
- 可加入「页级 rerank / 章节级摘要」与跨页一致性校验。
- 编译可做断点持久化（当前为同源 `source_hash` 复用，进程内一次性跑完）。
