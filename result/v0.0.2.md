## 一、目标

日志分析 agent 被问到「PCIe 如何加载」这类问题时，正确答案往往**跨组件**：一个组件的行为
依赖另一个组件经 mdb 总线生产的数据。要评估 agent 是否真做了「跨组件根因溯源」（而非止步于
复述单条日志），需要把这些真实链路沉淀成**可自动打分的标准答案（groundtruth）**。

## 二、方法

### 1. 跨组件通信机制（被测对象）
openUBMC 组件不直接函数调用，而是经 mdb 总线解耦，三类交互：
- **属性订阅**：消费方 `client:On<X>PropertiesChanged` 订阅生产方拥有的接口属性；
- **主动读对象**：`client:Get/Foreach<X>Objects` 或 `mdb.get_object`；
- **服务方法调用**：`bus:pcall(<service>, ...)` 调别组件方法。

接口 owner（生产方）= 在自己 `mds/model.json` 定义并 `set_prop` 实现该接口的组件。

### 2. 依赖图自动初筛 + subagent 实地核对
先用脚本扫各组件 `src` 里实际 wired 的 `client:On<X>` / `get_object` / service 调用，
解析到目标接口、再用各组件 `mds/model.json` 反查 owner，得到候选依赖边；再对每条边派
**一个 subagent 实地打开两端源码核对**，要求：亲自看过的 4~6 个跨双组件 `file:line` 锚点、
至少 1 条代码里真实打印的日志串、并判定机制（订阅/读取/调用）。

**核对纠正了 2 条初始假设**（体现实地核对的价值）：
- `pcie_device ⟷ storage` 的 `PcieAddrInfo`：方向反了——实际是 **storage 主动读 pcie_device**
  的对象算 NVMe 盘的 ResouceId，owner 是 pcie_device。
- `sensor → fault_diagnosis`：sensor 根本没调；真实调用方是 **pcie_device**（OCP 热插/带内
  拓扑上报时 `bus:pcall` 调 `CmdInfo.Process`），且 fault_diagnosis 实现不在快照内。

### 3. golden case schema（对齐既有 evaluator，可自动打分）
每条用例 = 一条跨组件流程，字段：
- `input.questions`：**多问法**（短句 / 引导长句 / 模糊故障代入 / **日志驱动**——引用真实日志串），
  测意图识别鲁棒性；
- `expected_output`：`reference_answer`（给 LLM 裁判）、`root_cause_keywords`、
  `expected_components`（多组件）、`expected_citations`（6 个跨双组件锚点，从严）、
  `expected_tools` + `must_use_source`、`dependency_edge`；
- `metadata`：`flow_chain` / `interface` / `properties` / `log_evidence`（真实日志模板→源码位置）。

### 4. 评测器改造（多组件 / 多问法）
- `evaluators.component_named`：支持多组件、按命中比例打分（单组件退化为 1.0/0.0，向后兼容）；
  `coerce_expected` 合并 `expected_component(s)` 为去重保序列表。
- `run_eval._expand_questions`：把 `input.questions` 展开成共享同一 `expected_output` 的独立
  子项（打 `case_id/variant_index` 标签）；向后兼容旧的单 `input.question`。

### 3. 结论
1. **答得"像对的"但没溯源**：组件点名（0.90）、根因词命中（0.98）都很好，但
   `citation_match=0.07`、`rootcause_correctness=0.35`——agent **止步于日志/表象，没追到
   「谁订阅、谁生产」的真链路锚点**（订阅点、`set_prop` 生产点）。这正是本 groundtruth 的价值：
   把「看着对 vs 真溯源」的差距量化出来了。
2. **问法影响明显（意图识别有效）**：**模糊症状**问法让组件识别（0.98）与忠实度（0.61）最高；
   **日志驱动**问法根因命中最高（0.45）却忠实度最低（0.35）——顺着日志走、没回源码验证。
3. **数据集偏置已确认**：因为所有用例的日志集都种了答案行，`citation_match` 普遍被压低。
   要纯测溯源能力，需做「只给症状、不给答案行」的对照组（见第六节）。

> 历史：本版先做过一次 2 问法冒烟（仅 xc-pcie-bios-bdf），结论与全量一致
> （`citation_match=0`、`rootcause_correctness=0.1`），此处不再单列。

## 五、运行方式

```bash
cd backend && source venv/bin/activate
# 数据集（若无）：用真实日志模板合成 eval_bmc_applog（见提交记录脚本）
python -m eval.run_eval --offline --run-name xc-full \
  --cases eval/datasets/cross_component_cases.json
```
注：需 `LLM_API_KEY`（agent 产出回复 + LLM 裁判）。每变体是一整个 ReAct 循环
（多轮迭代 LLM 调用）+ 3 次裁判调用，离线串行，45 变体耗时约 90 分钟（受 provider 延迟/重试影响）。

## 六、后续可改进
- 造一份「只有症状、不含答案行」的日志集对照跑，纯测源码溯源能力（看 `citation_match` 能到多少）。
- 继续扩边：`network_adapter ⟵ {frudata, fructrl, general_hardware}`、`power_mgmt ⟵ fructrl` 等。
- `citation_match` 目前按 basename:line 匹配，跨组件同名文件（model.json/client.lua）存在误配可能，
  可加组件名前缀消歧。
- 离线 runner 可加并发 + 支持更便宜的 `JUDGE_LLM_MODEL` 以缩短全量耗时。
