# v0.0.3 — 多 Agent 架构（检索子 Agent）落地 + 与单 Agent 对比评测

日期：2026-07-11
架构：`AGENT_SOURCE_MODE=direct`（单 Agent，现状基线）vs `AGENT_SOURCE_MODE=subagent`（主 Agent + 检索子 Agent）
模型：deepseek-v4-pro（agent 与裁判同款）；用例：黄金集 43 条（`--user-id 1`）

## 方法

同一份黄金用例集、同一模型、同一迭代预算（主 Agent 10 轮），只切换取证方式：

- **direct**：主 Agent 直连 8 个源码工具 + 3 个 wiki 工具（单 Agent 现状）。
- **subagent**：主 Agent 只见 log 工具 + 单一取证工具 `retrieve_evidence`；源码/wiki
  检索由无状态检索子 Agent 承担（≤6 轮小循环，标准查法写在其提示词里：代码先
  `trace_call_chain` 骨架后 `gather_code_context` 函数体、wiki 先目录后整页），
  只带回 ≤2KB 摘要 + 真实到访的出处。

每架构 2 分片并行离线跑（`python -m eval.run_eval --offline --arch <mode> --user-id 1`），
run 明细在 `data/eval_runs/v002-{direct,subagent}-p{1,2}.json`（gitignored）。

**重要修复（影响历史基线解读）**：`run_eval` 构造 `LogDataset` 从未注入 `user_id`，
导致 v0.0.0/v0.0.1 的所有评测里源码工具调用 100% 报「源码索引需登录后可用」
（如 xc-full run：88/88 全错）——旧基线的 rootcause/faithfulness 低分很大程度源于此，
不能与本版数字直接纵向比较。本版起 `--user-id` 注入已修复。

**覆盖率注意**：评测中途 DeepSeek API 余额耗尽（402 Insufficient Balance），
direct 完成 28/43，subagent 完成 12/43。为公平起见，下表只统计**两边都成功产出
回复的 12 条配对 case**（easy 2 / medium 5 / hard 5，含 xc 跨组件难题）。样本偏小，
方向性结论明确、具体数值有波动空间；余额充值后可用同一命令补全全量对比。

| faithfulness（裁判） | 0.45 | **0.56** | +0.10 |

`subagent_empty_handed`＝0.00（没有空手而归）；每 case 取证 1~10 次、平均 4 次。

## 结论

1. **质量全面胜出**：诊断准确率、根因正确性、引用落地、可执行性全部显著提升，
   且 12 条里 direct 有 5 条把 DSML 工具调用标记泄漏进最终回复（烧满 10 轮后被
   强制收尾、模型仍试图调工具），subagent 一条都没有——把「读得多」的活隔离出去后，
   主 Agent 不再被撑爆，能正常收口。
2. **主 Agent 上下文瘦身 8 倍**（382k→48k 名义 token/case），架构讨论时的核心关切
   （主 Agent 上下文不能撑爆）得到验证。
3. **代价是取证侧 token 放大**：总名义 token 约 2.9×。两个原因：主 Agent 取证次数
   偏多（平均 4 次/case，最多 10 次，prompt 建议是 1~2 次）；子 Agent 平均 5.47 轮、
   贴着 6 轮封顶跑（每轮重发自己的上下文）。名义值含 DeepSeek 前缀缓存命中
   （计费约为未命中 1/10），实际费用放大倍数低于 2.9×。

## 追加实验 A：前缀缓存命中率拆解（2026-07-11）

按角色拆开统计本轮评测的 DeepSeek 前缀缓存命中（命中计费约为未命中 1/10）：

| 角色 | cache_hit | cache_miss | 命中率 |
|---|---|---|---|
| direct 主 Agent | 2.1M | 8.2M | **20%** |
| subagent 主 Agent | 424k | 114k | **79%** |
| subagent 子 Agent | 5.6M | 7.0M | 44% |

- direct 只有 20% 的根源：`context.py` 的旧工具结果省略是**每轮多省一条**的渐进式
  改写——省略线逐轮后挪，改写点之后整段历史对缓存都是新前缀。direct 模式源码工具
  单条 10~18KB，第 3~4 轮起轮轮超 24k 预算、轮轮改写。省 token 和吃缓存两个目标打架。
- subagent 主 Agent 79%：上下文只积累 ≤2KB 摘要，从不超预算 → 省略从不触发 →
  前缀只增不改（架构红利的直接证据）。
- 子 Agent 44%：无状态设计的固有代价（每次取证冷启动，第 1 轮全额重算）。

图解（含修复方案「跳变后冻结」）：https://claude.ai/code/artifact/670e8b1b-f975-4cc1-b070-24f254e21d55

## 追加实验 B：单 Agent 放宽到 40 轮（2026-07-11，2 条 case）

问题：单 Agent 的失败是不是轮次预算不够？把 `AGENT_MAX_ITERATIONS` 提到 40
（同时 `AGENT_MAX_HISTORY` 40→160，否则消息窗口会把用户问题挤出上下文），
选两条 direct@10 全 0 分 + DSML 泄漏的 case 重跑：

| case | direct@10 | direct@40 | subagent |
|---|---|---|---|
| 电源休眠 (hard) | 10 轮打满，全 0 分，DSML 泄漏 | **15 轮自然收口**，diag 1.0 / root 0.9，815k tok | diag 1.0 / root 1.0，1.70M tok |
| PCIe oob (medium) | 10 轮打满，全 0 分，DSML 泄漏 | **烧满 40 轮仍全 0 分 + DSML 泄漏**，61 次工具调用，1.29M tok（9×成本） | diag 1.0 / cite 1.0，1.87M tok |

结论：**轮次只救"差一口气"的 case（甜点位约 16~20 轮），救不了上下文已被省略
机制掏空的 case**——后者给 4 倍预算、9 倍 token 结局一模一样：旧证据被换成占位符
→ 模型觉得"还差一点"→ 继续查 → 新结果又被省略，在 24k 单上下文里死循环。
瓶颈是上下文容量与管理方式，不是轮次。多 Agent 等于给了同一条 case 十几个独立的
6 轮小上下文，所以能做对。明细：`data/eval_runs/v002-direct-i40.json`。
