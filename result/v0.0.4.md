# v0.0.4 — claw-code 风格上下文压缩替换丢弃式省略（缓存命中率修复）

日期：2026-07-12
动机：v0.0.3 追加实验 A 定位到 direct 模式主 Agent 前缀缓存命中率仅 20%，根源是
「每轮多省一条」的渐进式省略逐轮改写历史前缀；追加实验 B 证明被省略机制掏空的
上下文给 40 轮也救不回来。本版参照 claw-code（Claude Code）的上下文压缩机制
（检测 → 摘要 → 压缩 → 恢复流水线）重写收缩策略。

## 机制（`backend/agent/compaction.py` + `context.py`）

- **确定性模板摘要，不调 LLM**：七段式（Scope 角色计数 / 工具清单 / 最近用户请求 /
  中英关键词待办推断 / 关键文件引用（lua/c/cpp/py/log 等 + `file:line`）/ 当前工作 /
  逐条时间线，各字段截断）——计数+取值+关键词匹配+截断，零延迟零成本零幻觉；
  LLM 只是压缩结果的消费者。
- **触发式 + 冻结**：历史估算超 `AGENT_CONTEXT_TOKEN_BUDGET`（24k）才压缩；
  分割点 `upto` 与摘要持久化在 `Session.compaction`，两次触发之间**冻结**，
  发给 LLM 的前缀逐字节稳定；`session.messages` 永远 append-only（前端历史不受影响）。
- **边界安全**：分割点不落在 `role:"tool"` 消息上（回退循环保住 tool_calls 配对，
  否则 DeepSeek 400）。
- **二次压缩合并 + 预算裁剪**：旧摘要与新摘要合并仍是七段结构（Scope 累加、
  工具并集、pending/files 去重、时间线只留新的）；超 4000 字符按
  pending > current > files > requests > timeline 优先级行级裁剪。
- 开关：`AGENT_CONTEXT_COMPACTION=compact`（默认）|`elide`（旧机制保底，A/B 可回切）；
  `AGENT_COMPACTION_PRESERVE_RECENT=4`。

## 首版实测暴露 churn 缺口 → 低水位 + 显著性护栏

首版实现（触发条件=超预算且分割点可推进）在实测中复发了前缀改写病：一条巨型工具
结果（`list_source_files` 全量清单，估算 ~180k token）卡在「固定保留最近 8 条」窗口
里，怎么压都超预算 → 10 轮压 3 次、轮轮改写前缀，命中率掉到 **13%**、token 涨到
627k（elide 同 case 142k）。修复（`_compute_compaction` 重写）：

1. **低水位跳变**：触发时分割点只推进到「尾部估算 ≤ 预算×60%」即停——保住尽量多
   的近期上下文，又留出增长空间，不会下一轮又贴线触发；
2. **显著性护栏**：低水位够不着（巨型消息仍在保留窗内）时，仅当本次推进能砍掉
   ≥30% 尾部才压缩，否则冻结等它滑出窗口——不为省 2% 的 token 付一次全量重算；
3. 保留窗语义「固定 8 条」→「**最少** 4 条」，巨型结果更快滑出窗口；
4. 条数兜底（尾部条数超 `max_history`）时一次推进到上界。

## 实测（2 条 case：PCIe oob(medium) / 电源休眠(hard)，deepseek-v4-pro）

**缓存与成本（压力位：PCIe oob case，工具结果最大最密）**

| 配置 | 命中率 | 总名义 token | 压缩触发 |
|---|---|---|---|
| elide @10（v0.0.3 基线） | 50% | 142k | —（每轮改写） |
| elide @40 | 50% | 1289k | —（每轮改写） |
| compact 首版 @10（churn 缺口） | **13%** | 627k | 10 轮 3 次 |
| compact 修复 @10 | 54% | 132k | 未触发（本轨迹未超预算） |
| compact 修复 @40 | **76%** | 854k（-34% vs elide@40） | 37 轮 6 次（约 5-6 轮一次） |

@40 压力测试是机制的真考场：触发点全部落在 25-29k（刚过预算线），压到低水位后
冻结 5-6 轮，命中率 50%→76%；按「命中计费≈未命中 1/10」折算，实际费用约为
elide@40 的 40%。

**质量（同 2 条 case，对照 v0.0.3 各配置）**

| case | elide@10 | compact@10 | compact@40 | （参照）subagent 多 Agent |
|---|---|---|---|---|
| 电源休眠 (hard) | 全 0 分 + DSML 泄漏 | **diag 1.0 / root 1.0 / cite 1.0**（9 轮收口） | diag 1.0 / cite 1.0 / root 0.4* | diag 1.0 / root 1.0 |
| PCIe oob (medium) | 全 0 分 + DSML 泄漏 | 全 0 分 + DSML 泄漏 | 全 0 分 + DSML 泄漏 | **diag 1.0 / cite 1.0** |

\* root 0.4 为裁判抖动（同 case 其他轮 0.9/1.0）。

## 结论

1. **压缩机制达成设计目标**：前缀在触发之间逐字节冻结，长循环（@40）命中率
   50%→76%、总 token -34%；触发节奏受低水位/护栏控制，churn 已根治（有专门的
   逐字节前缀稳定测试固化）。
2. **证据保留改善了可解 case**：电源休眠 case 在 compact 下稳定满分（elide 下全 0
   + DSML 泄漏），且 @10 就能收口——摘要式压缩保住了「已查证事实」，模型不再
   反复重查。
3. **压缩救不了单 Agent 的病态 case**：PCIe oob 在任何轮次预算下仍 0 分——它需要
   的是多路独立取证（subagent 架构下 diag 1.0），再次印证 v0.0.3 结论：这类 case
   的瓶颈是单上下文形态本身，不是上下文管理技巧。
4. 样本量注意：n=2、LLM 轨迹方差大（temperature 0.3）、裁判有抖动；缓存结论
   （命中率/触发节奏）是机制性的、可信度高，质量结论方向可信、数值待全量评测确认。
